# Data service: the spec and its lifecycle

- Author: @niveathika
- Reviewers: 
- Created: 2026-09-18
- Updated: 2026-09-18
- Issue: [#1503](https://github.com/ballerina-platform/ballerina-spec/issues/1503)
- Status: Submitted

## Summary

A data service is generated by the **existing `persist` build tool**, through one new command
and one new options group. It reads a hand-written spec file in `persist/`, validates it
against the persist model, and generates HTTP and GraphQL services into one module.

```
bal persist add --dataservice http,graphql   # register, and record the protocols
# write persist/model.bal, or bal persist pull
bal persist expose                           # derive persist/service.bal from the model
bal build                                    # client and services are generated
```

Please add any comments to issue [#1503](https://github.com/ballerina-platform/ballerina-spec/issues/1503).

## Goals

- Generate a working data service from an existing persist model.
- Derive the spec from the model the way `persist pull` derives the model from a database.
- Keep every hand-written file in `persist/`, every generated file in `generated/`.
- Add exactly one command to `persist`, and leave every existing command's behaviour
  unchanged.

## Non-goals

- OData and SOAP.
- Interceptors and hooks. The generated services declare their own listeners; code-level
  extension seams are deferred.
- One data service spanning several persist stores, and more than one persist model in a
  package — the scope decisions are restated in full below.

**Part A** is what the user writes: one protocol-neutral model of what the API exposes, from
which HTTP and GraphQL are two renderings. **Part B** is how it is produced, validated and
built — one new command on `bal persist`, one options group in `Ballerina.toml`.

Everything marked ✅ was compiled and executed, not reasoned about.

---

## Part A — the spec language

What a data service exposes, expressed once, independently of protocol.

### 1. Three models, not one

Most of the confusion in this design has come from treating these as one thing.

| | What it holds | Owner |
|---|---|---|
| **Data model** | entities, fields, types, keys, relations | persist, `model.bal` — exists today |
| **Service model** | what the API exposes: operations, query capability, payload shapes, errors | **this document** |
| **Protocol binding** | how the service model is rendered on one wire: paths, methods, encoding | generated, one per protocol |

`?filter={...}` versus `filter[x$gt]=` is a **binding** question. "`grade` may be filtered by
equality and set membership" is a **service model** question. They were repeatedly argued as if
they were the same question.

#### A second distinction, inside the service model

| | Lives in | Example |
|---|---|---|
| **Capability** | the service model, design time | "`grade` admits `EQ`, `IN`" |
| **Query** | produced by the binding, per request | "`grade IN (SENIOR, LEAD)`" |

The runtime `Query` type — `Filter`, `SortKey`, `Page` — is specified in `query-model.md`. This
document is about the capability side, and about everything that is not query.

### The spec file

`persist/service.bal` declares **one service object type for the whole API**, and that root
type is what gets deployed:

```ballerina
import ballerina/dataservice;

public type Employee record {| string name; string? email?; |};
public type Department record {| int id; string name; |};

@dataservice:ServiceConfig {defaultPageSize: 25, maxPageSize: 500}
@dataservice:Http {basePath: "/api/v1"}
public type StoreApi service object {
    *dataservice:Service;

    resource function get employees(EmployeeFilter filter, dataservice:Page page)
        returns Employee[]|dataservice:Error;
    resource function get employees/[int id]() returns Employee|dataservice:Error;

    resource function get departments(dataservice:Page page)
        returns Department[]|dataservice:Error;

    // both directions of the relation
    resource function get departments/[int id]/employees(EmployeeFilter filter,
            dataservice:Page page) returns Employee[]|dataservice:Error;
    resource function get employees/[int id]/department() returns Department|dataservice:Error;
};
```

#### Why one root type, not one type per entity

A per-entity shape — `EmployeeApi`, `DepartmentApi`, composed with `*EmployeeApi;` into a
root — compiles, and it reads well for entities in isolation. It was rejected because
**a relation resource belongs to two entities and therefore to neither type.**
`departments/[id]/employees` is rooted at the department path but returns `Employee[]` and
takes an `EmployeeFilter`. Wherever it is put, the composition stops being a clean partition,
and the one benefit that shape was for — *drop `*DepartmentApi;` to unpublish an entity* —
stops being true, because the department type is still reachable through
`employees/[id]/department`.

It also buys less than it looks for regeneration. `expose` appending a new entity that has a
relation to an existing one has to reach *inside* an existing type either way, so composition
does not make the additive rule easier to honour.

The spec declares its own payload types and does **not** import the generated module.
`persist/` is not a package source root, so the spec has to stand on its own. Its only
imports are `ballerina/dataservice` and whatever the payload types need — never
`ballerina/http` or `ballerina/graphql`.

#### Root type name

| Case | Root type |
|---|---|
| root model | `<PackageName>Api` — package `app` gives `AppApi` |
| named model `sales` | `<ModelName>Api` — `SalesApi` |

Both are known at `add` time. Since the spec is a hand-written file and regeneration is
additive-only, renaming the root is safe: the generator uses whatever name it finds.

#### Protocol comes from the toml, not the spec

**Reverses D65.** The generator reads `options.dataservice.protocols` from `Ballerina.toml`. The spec's
root type includes only `*dataservice:Service` and names no protocol:

```ballerina
@dataservice:ServiceConfig {defaultPageSize: 25, maxPageSize: 500}
public type StoreApi service object {
    *dataservice:Service;            // neutral — never *http:Service or *graphql:Service
    ...
};
```

D65 read the protocol from the root type's inclusion — `*http:Service` versus
`*graphql:Service` — on the grounds that a single `options.dataservice` *string* could not
express two protocols at once. That much was right. An **array** can, and the inclusion
approach carried a cost D65 did not price:

| | Inclusion (D65) | `options.dataservice.protocols` |
|---|---|---|
| Two protocols need | a second root type **and** a second spec file | one more array element |
| Resource list, filter types, payload types | **written twice** | written once |
| Add an entity | `sync` twice, or they drift | `sync` once |
| Delete a resource | delete it twice, or one protocol keeps serving it | delete it once |
| Default spec file | names its protocol | **names no protocol at all** |

The last row is the point. Proposal 2 claims the service model is protocol-independent; a
spec file that must include `*http:Service` is not. With the list in the manifest, protocol
names enter the spec only through the optional `@dataservice:Http` / `@dataservice:Graphql` overrides, and only
when a user deliberately diverges from a default.

What survives from D65 is the finding behind it — both type declarations do compile in one
file, in a package importing `ballerina/http` and `ballerina/graphql`. That is still what
makes two generated services in one module legal.

### 2. Base path

Every protocol has exactly one mount point: HTTP base path, GraphQL service path, SOAP
endpoint, OData service root. **The concept is neutral; the value is not.**

An earlier draft held one string for all bindings. That does not survive contact with the
protocols:

| Binding | What the mount point *is* | Conventional value |
|---|---|---|
| HTTP | a path **prefix**; resources hang below it | `/api` |
| GraphQL | the **entire** endpoint; nothing hangs below it | `/graphql` |
| SOAP | the endpoint | — |
| OData | the service root, with a mandated grammar below it | — |

So the model holds **one mount point per protocol**, defaulted per binding and overridable:

```ballerina
@dataservice:Http    {basePath: "/api/v1"}
@dataservice:Graphql {basePath: "/graphql"}
```

Both annotations are **optional**. With neither, the defaults in Part B apply and the spec
file names no protocol at all. Which protocols exist is declared in `Ballerina.toml`, not here
— an annotation for an undeclared protocol is an error.

Because the two protocols are generated onto **separate listeners and ports**, the values never
collide, and `/api/v1` on both is legal if that is what someone wants.

#### Versioning is an HTTP claim, not a neutral one

The earlier draft also called base path "the only versioning mechanism in the model". That is
HTTP reasoning. GraphQL does not version by path — schema evolution with field deprecation is
the norm, and `/api/v1/graphql` reads as a category error to a GraphQL consumer. So: **path
versioning is available in the HTTP binding, through `@dataservice:Http {basePath}`, and is not offered
as a neutral facility.** Note also that the HTTP default is `/api` with no version segment, so
versioning is a deliberate act rather than a scaffold default.

### 3. One addressing vocabulary, borrowed from the persist client

Path and method mean different things in each protocol, and two of the four have neither:

| Protocol | Addressing |
|---|---|
| HTTP | path + method — `GET /employees/{id}` |
| OData | path + method, but **its own mandated grammar** — `/Employees(4)` |
| GraphQL | **no paths, no methods.** One endpoint; operations are fields on `Query`/`Mutation` |
| SOAP | **no paths, no methods.** One endpoint, always POST; operations are body elements |

So the model cannot use any one protocol's addressing. It uses **the persist client's**, and
every binding translates from that.

That is not a neutral third invention. It is the vocabulary of the layer directly underneath,
read from a real generated client:

```ballerina
resource function get    departments()
resource function get    departments/[int id]()
resource function post   departments(DepartmentInsert[] data)
resource function put    departments/[int id](DepartmentUpdate value)
resource function delete departments/[int id]()
```

A reader moving between the persist client and the service model sees one shape. That is worth
more than avoiding the HTTP-flavoured verb names, because the accessors are the language's own
resource accessors, not HTTP's.

| Model | HTTP | GraphQL | SOAP |
|---|---|---|---|
| `get emps` | `GET /emps` | `Query.emps` | `<ListEmps>` |
| `get emps/[int id]` | `GET /emps/{id}` | `Query.emp(id:)` | `<GetEmp>` |
| `post emps` | `POST /emps` | `Mutation.createEmp` | `<CreateEmp>` |
| `put emps/[int id]` | `PATCH /emps/{id}` | `Mutation.updateEmp` | `<UpdateEmp>` |
| `delete emps/[int id]` | `DELETE /emps/{id}` | `Mutation.deleteEmp` | `<DeleteEmp>` |

One wrinkle to know about. Persist's `put` is a **partial** update, and §5 maps partial update
to HTTP `PATCH`. So model `put` becomes wire `PATCH`. Model and wire disagree on that one name.

#### Why arbitrary paths are rejected

Not on taste. **The generator has to produce a body**, and to do that it must know which entity
and which operation a resource means. A persist-shaped path carries that information; a
free-form path carries none.

This is D49 restated: every resource is either **CRUD-derivable** or carries **`@Override` with
a query**. Arbitrary paths are not forbidden — they are the Override case, where the user
supplies the thing the generator could not derive.

#### Naming is the user's choice; structure is not

Protocols disagree about naming: REST wants `/employees`, OData wants `/Employees`, GraphQL
wants `employees`. So the model holds a **canonical name per entity**, and each binding applies
its own casing and pluralisation rule. The user picks the canonical name, not the URL shape.

Azure DAB found per-entity casing insufficient and made naming overridable per protocol
(`rest.path` versus `graphql.type.singular/plural`). We will probably need the same eventually.

### 4. Read operations

Per read operation the model holds:

| | |
|---|---|
| **Cardinality** | single or collection. Decides 404-vs-empty-array, and GraphQL nullability |
| **Result shape** | which view type; this is what narrows the `SELECT` |
| **Query capability** | filterable fields and the operators each admits, sortable fields, selectable fields, page defaults and caps |

Response *format* is not in the model. The shape is; JSON versus XML versus a GraphQL selection
set is binding.

#### Field selection: the exposed type's optionality declares it

Three states per field, and **no separate selection type is needed**:

| Field in the exposed type | Meaning |
|---|---|
| absent | not exposed at all |
| required — `string name;` | always returned |
| optional — `time:Date hiredOn?;` | **selectable**; the caller may omit it |

```ballerina
public type Employee record {|
    // int id;            not exposed — delete the field to withhold it
    string name;          // always returned
    string? email?;       // selectable
    time:Date hiredOn?;   // selectable
    EmployeeGrade grade;  // always returned
|};
```

`string? email?` stacks two different things: `string?` is a nullable column, `email?` is a
field the caller may omit from the response. They are orthogonal and both are needed.

**No selection enum and no `<Entity>Optionalized` response type are needed.** Only the
selectable fields are optional, so `name` and `grade` stay guaranteed in every response,
`@constraint` on them stays meaningful, and the response schema says what is actually true. A
scheme that optionalized the whole response type would have to declare every field optional,
including the key.

#### Selection is capability, not pushdown

Whether that subset reaches the `SELECT` is a **binding** question, and today the answer is no
in either protocol — persist's `targetType` is a compile-time typedesc, so we fetch the full row
and trim the response. The payload shrinks; the database work does not. GraphQL already behaves
exactly this way (proposal 3), and HTTP has the same limit. A performance caveat to document,
not a reason to leave selection out of the model.

#### Filter capability: one line per field, listing its operators

```ballerina
public type EmployeeFilter record {|
    dataservice:Operation[] email = [dataservice:EQ, dataservice:IN];
    dataservice:Operation[] grade = [dataservice:EQ, dataservice:IN];
    dataservice:Operation[] hiredOn = [dataservice:GTE, dataservice:LTE];
    dataservice:Operation[] name?;   // no initializer = every operator valid for the type
|};
```

| Field state | Meaning |
|---|---|
| absent | not filterable |
| present, no initializer | every operator valid for that field's type |
| present with an array | only those operators |

**This type is declarative, not the runtime type.** The generator derives the input type from
it — `record {|string eq?; string[] anyOf?;|} email?` and so on — so the type named in the spec
and the type in the generated contract are different. That is the same source-versus-copy
relationship that makes `@constraint` work on payload types, but it is a bigger swap than those,
and a reader should not assume the spec type is the wire type.

The alternative, a nested record per field, is the runtime type directly and needs no
derivation. It was rejected on two counts: it repeats the field's type inside every operator
record, and it is very hard to render in a form, where an operator array is a checkbox group.

#### The operator enum, and why member names are not wire names

`Operation` is one flat enum, not partitioned per type family. A partitioned set (`StringOp`,
`ComparableOp`) compiles and would catch `[GTE]` on a string field at compile time — but the
compiler cannot link `EmployeeFilter.email` to `Employee.email`, since the spec does not
reference the entity, so the plugin has to check operator-against-field-type regardless.
Partitioning buys a weaker second check at the cost of a taxonomy to learn.

✅ **The member name and the wire name have to be separate**, verified by compiling:

| Member | Wire / input field | Valid for |
|---|---|---|
| `EQ`, `NE` | `eq`, `ne` | any |
| `IN`, `NOT_IN` | **`anyOf`**, `noneOf` | any |
| `LT` `LTE` `GT` `GTE` | `lt` `lte` `gt` `gte` | comparable |
| `LIKE` `STARTS_WITH` `ENDS_WITH` `CONTAINS` | `like` `startsWith` `endsWith` `contains` | string |
| `IS_NULL` | `isNull` | nilable |

`IN` is fine as an enum member — uppercase, so no clash with the `in` keyword. But `in` **cannot**
be an unescaped record field name (`invalid token 'in'`), and the escaped `'in` leaks the quote
into JSON keys and GraphQL input fields, exactly as D18 records for `'limit`. Hence `anyOf` on
the wire.

#### Sort capability: the field whitelist, and nothing else

```ballerina
public enum EmployeeSortBy { name, hiredOn, grade }

resource function get employees(EmployeeFilter filter, EmployeeSortBy[] sort,
        dataservice:Page page) returns Employee[]|dataservice:Error;
```

**Direction is not declared, because it is not a capability.** "Which fields may be sorted" is
design time; "sort by `hiredOn` descending" is per request. A `record {| EmployeeSortBy column;
Direction direction = ASC; |}` puts a runtime value in a design-time slot.

And unlike filter operators, direction is symmetric. `STARTS_WITH` genuinely does not apply to a
date, so operators have to be declared per field — but there is no such thing as an
ascending-only field, so there is nothing to restrict.

`dataservice:Direction` still exists in the shared module: the **derived** runtime type needs it,
and it is the GraphQL `orderBy` input enum. It simply does not appear in the spec.

| | HTTP | GraphQL |
|---|---|---|
| Declaration | `EmployeeSortBy[] sort` | same |
| Wire | `?sort=-hiredOn,name` | `orderBy: [{hiredOn: DESC}, {name: ASC}]` |

The HTTP form takes JSON:API's leading-minus convention, so one parameter carries field and
direction together and no second `direction` parameter is needed.

#### Unsorted reads order by primary key

**Required, not a nicety.** Offset pagination over an unordered result is unsound: the database
may return rows in a different order between two queries, so page 2 can repeat or skip rows from
page 1. So when a request carries no sort, the generated query orders by the entity's primary
key.

Azure DAB does the same — its `$first` documentation states results are "ordered by primary key
by default". For a composite key, all key segments in declaration order.

#### Page: `count` and `offset`

```ballerina
public type Page record {|
    int count = 25;
    int offset = 0;
|};
```

✅ **Not `limit`.** `limit` is a Ballerina keyword and fails as a field name outright
(`invalid token 'limit'`); `'limit` compiles but is the D18 leak. `count` matches the HTTP query
parameter proposal 2 already specifies, so one name serves the record field and the wire.

### 5. Write operations

| Operation | Input | Output | The rule that matters |
|---|---|---|---|
| create | subset of insertable fields | created entity or key | **must be total** |
| update | partial, key excluded | updated entity | key in the payload is an error |
| delete | key only | deleted entity or nothing | — |

**Totality is the load-bearing rule.** For every required field of `<Entity>Insert`, the field
must be present in the create payload, or database-generated, or nilable, or defaulted in the
spec. If none holds, creation is impossible and the tool must say so, naming the field. This is
what stops type narrowing from sliding until the generated insert cannot be built.

### 6. Errors are neutral, and have to be

| Neutral error | HTTP | GraphQL | SOAP |
|---|---|---|---|
| `NotFound` | 404 | error entry | fault |
| `AlreadyExists` | 409 | error entry | fault |
| `ConstraintViolation` | 400 | error entry | fault |
| `Internal` | 500 | error entry | fault |

If this set is not in the model the four bindings drift, and the same failure means different
things depending on which protocol a client happened to use. A missing resource is **404, not
200 with an empty body** — Azure DAB does the latter and its own docs admit clients must
special-case it.

### 7. Relations — and the GraphQL service class

The model says only: **which relations are navigable, and whether they are read-only**. How that
is addressed is binding:

| Binding | Rendering |
|---|---|
| HTTP | sub-resource — `GET /departments/{id}/employees` |
| GraphQL | a **resource method on a service class** |
| SOAP | a nested element, or a separate operation |
| OData | `$expand`, or a navigation property path |

#### ✅ Verified: the service class is how GraphQL expresses this, and it resolves lazily

Probed against a running `ballerina/graphql` service. An entity returned as a
`distinct service class` becomes a GraphQL `OBJECT`, and each `resource function get` becomes a
field:

```ballerina
public distinct service class Employee {
    resource function get id() returns int => self.id;
    resource function get name() returns string => self.name;
    resource function get department() returns Department { ... }   // the relation
}
```

```
schema:  OBJECT Query      fields: employees
         OBJECT Employee   fields: id, name, department
         OBJECT Department fields: id, name
```

Two results that matter, both from the resolver trace:

**Field resolvers are lazy.** `{ employees { id name } }` — the `department` resolver **never
ran**. So an unrequested relation costs nothing, which a record-returning resolver cannot give
you, because a record is fully constructed before it is serialised.

**N+1 is real and visible.** `{ employees { id department { name } } }` ran the department
resolver **once per parent**:

```
>> employees resolver RAN
>> department resolver RAN for employee 1
>> department resolver RAN for employee 2
```

`ballerina/graphql` ships `DataLoader`, so the fix exists, but the generator has to emit loaders
rather than plain resolvers. Not free, and it should be a stated TODO rather than a surprise.

#### What this means for the model

The service class **is** the declaration — no annotation describes the inner type, exactly as a
resource signature is the declaration elsewhere. So the model's *result shape* must be able to
render two ways:

| Binding | Result shape renders as |
|---|---|
| HTTP, SOAP | a **record** — eager, all fields present |
| GraphQL | a **service class** — one resolver per field, lazy |

That is one neutral concept (an exposed type with a field list and relations) with two
renderings. It also means **GraphQL should generate service classes, not records**, at least for
entities with relations — otherwise laziness and any future DataLoader fix are both off the
table.

#### Exactly one hop, and that is a persist constraint

persist's generated types cap relation nesting at one level, structurally:

```ballerina
public type DepartmentWithRelations record {|
    *DepartmentOptionalized;
    EmployeeOptionalized[] employees?;    // Optionalized, NOT EmployeeWithRelations
|};
public type DepartmentTargetType typedesc<DepartmentWithRelations>;
```

`employees` is `EmployeeOptionalized[]`, which carries no relation fields at all. **And you
cannot ask for more by declaring a deeper type — the type system refuses it.**

`targetType` is constrained to `typedesc<DepartmentWithRelations>`. `EmployeeOptionalized` is a
**closed** record, so no type that adds a `department` field is a subtype of it, which means no
two-hop type is a subtype of `DepartmentWithRelations` either.

✅ Verified by compiling a two-hop target type against the generated client:

```
ERROR incompatible types: expected 'DepartmentTargetType',
                          found 'typedesc<DepartmentWith2>'
```

One hop does work, against a live database — `{"id":1,"name":"Platform","employees":[{"name":
"Ama",...},{"name":"Bimal",...}]}`. Two hops does not compile. **So this is not a design choice
we are deferring; it is enforced upstream.** Reaching it
would need either `WithRelations` nesting to depth *n* upstream (combinatorial, and undefined
over a cycle) or the generated service assembling several queries by hand. Neither is in scope,
and neither is requested in proposal 4 — this is a stated limit of the feature, not a
prerequisite we are waiting on.

#### The relation is declared as a hierarchical path

A relation is declared in **both directions**, and the two signatures differ:

```ballerina
# to-many: takes filter, sort and page, because there are many rows
resource function get departments/[int id]/emps(EmpFilter filter, EmpSortBy[] sort,
        dataservice:Page page)
    returns Emp[]|dataservice:Error;

# to-one: takes none of them, because there is exactly one
resource function get emps/[int id]/department() returns Department|dataservice:Error;
```

The asymmetry is not an oversight. Cardinality decides the parameter list: there is nothing to
filter, sort or page on a single row. It also decides the return — `Emp[]` versus `Department`,
which is what gives HTTP its 404-versus-empty-array and GraphQL its nullability.

This matters more than it looks. An earlier draft used a flat name — `departmentEmps(int
departmentId, …)` — and that forced the GraphQL binding to *parse the method name* to work out
which type the relation hangs off.

The path states it structurally. `departments/[int id]/emps` reads directly as "attach `emps` as
a field on `Department`". No naming convention, no inference.

#### Why not an annotation, given only one hop is possible

Because **a relation collection needs its own filter, sort, select and page, and those live in
parameter types.** Only a resource method has parameters. An annotation can say which relations
are navigable and whether they are read-only; it cannot say that employees-within-a-department
are filterable by grade but not by `departmentId`. Annotation-declared relations would leave the
sub-resource with either no query capability at all, or a silent inheritance of the top-level
whitelist — and inheriting is wrong, since the parent key is already fixed by the path.

The volume objection is smaller than it looks. **G5 is deferred, so relations are read-only in
v1: one method per direction, not five.** A model with five relation edges is ten lines, and
`bal persist expose` writes them.

Where a bulk off-switch is wanted, it belongs at entity level and suppresses emission without
changing the declaration form:

```ballerina
@dataservice:Entity {relations: false}    // emit no relation resources for this entity
```

A depth *number* is a different concept and belongs at service level, as a runtime guard on
client-composed nesting in GraphQL — `@dataservice:Graphql {maxDepth}`, see §10. It is not a declaration.

### 8. Override

Validation the tool must perform:

- result columns of the query match the declared return type — names present, types assignable
- query parameters match the resource's declared parameters
- a read operation's query is a `SELECT`; no DML behind a read
- the return type is the schema — nothing is inferred from an entity

#### An override can carry filter, sort and page

You cannot append a `WHERE` to someone's SQL without parsing it — where does their `WHERE` end,
do they already have `GROUP BY`, `UNION`, `LIMIT`. You do not have to append. **Wrap**:

```sql
SELECT * FROM ( <the user's query> ) AS q
WHERE  ...        -- our clause
ORDER BY ...      -- our clause
LIMIT ...
```

The whitelist is then **the declared return type's fields**, and the `ColumnRef` entity alias is
the derived-table alias `q`. Same clause builder, no new machinery, and the user declares
filter and sort capability exactly as for a generated resource.

Caveat to document, not to block on: a predicate outside a derived table may not push down as
well as one inside it. Planners usually push for simple subqueries and usually do not when the
inner query has aggregates, `DISTINCT`, or its own `LIMIT`.

### 9. How the user gets a model

**Write it, or generate a skeleton and edit it.** `bal persist expose` produces a service
model from the persist model; the user then edits. The same answer covers three questions that
looked separate:

| Question | Answer |
|---|---|
| Which entities are exposed? | those present in the service model file — generated as a skeleton, then edited |
| Which fields are exposed? | **the return type of the service's function** — generated with basic filtering, edited if needed |
| Which relations are navigable? | generated as a skeleton, reviewed by the user |

So exposure is never a separate switch. Presence in the model *is* exposure, and the return type
*is* the field list — the same principle as D60, applied to three more concerns.

One consequence worth stating: because `pull` regenerates, it must not clobber user edits. That
is the same hazard already recorded against putting annotations in `persist/model.bal`, and it is
the strongest argument for the service model living in its own file that the user owns.

### 10. Deliberately not in the model

| | Why |
|---|---|
| Listener port, host, DB credentials | deployment config — `configurable`, `Config.toml` |
| **Auth mechanism** | the JWT validator or OAuth2 introspection setup is deployment config, for two independent reasons — see below |
| Response envelope / total count | v1 returns a plain array; `hasMore`, no total |

#### Auth: the scope is in the model, the mechanism is not

This supersedes the earlier "deferred to post-v1". D24 settled that auth must live in the spec,
because a strict contract rejects `@http:ResourceConfig` on the implementation — so it cannot be
added afterwards. Deferring the *feature* is fine; deferring the *slot* is not, because D47
makes regeneration additive-only and a later slot is a spec format change.

The split:

| | Where | Why |
|---|---|---|
| **Scope per operation** | the spec, as an annotation on the resource method | it is API surface, and the generator copies it into the contract |
| **Mechanism** — issuer, audience, JWKS URL, introspection endpoint, client credentials | `Config.toml`, with the listener | secrets do not belong in a checked-in spec, **and** annotation values must be constant expressions, so they cannot reference a `configurable` at all |

The auth probe compiled with literal values, so the second constraint has not been hit yet. It
is the harder of the two: it rules out inline mechanism config regardless of how we feel about
secrets in source.

Configurable naming follows D54. Rather than prefixing each of `issuer`, `audience`, `jwksUrl`,
`clientId` — all generic enough to collide — the service takes one nested record:

```ballerina
configurable AuthConfig auth = ?;
```

One name, namespaced fields, and a missing value is a config error rather than a silent default.

**Open, and blocking the neutrality claim: there is no GraphQL rendering.** `auth-findings.md`
is `ballerina/http` 2.16.6 only. `ballerina/graphql` does auth at service level via
`@graphql:ServiceConfig`; there is no per-resource equivalent to
`@http:ResourceConfig {auth: {scopes}}`. So scope-per-operation renders cleanly in HTTP and has
an empty cell for GraphQL. Three ways out — GraphQL enforces at service level only (which breaks
the §6 pattern, since the model would hold a concept one binding cannot render), the generator
emits field-level checks in the service class, or GraphQL auth is deferred. **Needs a probe
before proposal 3 commits.**

#### `maxDepth`

Service-level, and GraphQL-only in effect. HTTP sub-resources are emitted at a fixed depth by
the generator, so there is nothing to cap; GraphQL nesting is composed by the client at request
time, so it needs a runtime limit. This is the only place a depth number does real work.

### 11. The model in one table

| Concern | Service model holds | Binding derives |
|---|---|---|
| Base path | one mount point **per protocol**, defaulted per binding | a path prefix (HTTP) or the whole endpoint (GraphQL) |
| Operation | persist-shaped accessor + path | HTTP method + URL, GraphQL field, or body element |
| Naming | canonical name | casing and pluralisation |
| Read shape | exposed type + field list | record (HTTP/SOAP) or service class (GraphQL) |
| Query | **capability** — `Operation[]` per field, the sortable-field enum, page caps | the runtime input type, the wire encoding, and sort direction |
| Selection | **an optional field on the exposed type** | `$select`, a GraphQL selection set — trimmed in the response, never pushed down |
| Write | input type + totality rule | JSON, XML, or input object |
| Errors | neutral error set | 404, error entry, or fault |
| Relations | a hierarchical path, one hop | sub-resource, lazy resolver, `$expand` |
| Composite keys | consecutive path segments | multi-segment URL, or multiple arguments |
| Override | query + return type + capability | identical to a generated resource |
| Per-protocol exposure | `@dataservice:Expose {protocols}` | which bindings emit the operation |
| Auth scope | `@dataservice:Scopes` per operation | `@http:ResourceConfig {auth}`; GraphQL **unresolved** |
| Auth mechanism | *(not in the model — `Config.toml`)* | — |
| `maxDepth` | `@dataservice:Graphql {maxDepth}` | GraphQL runtime cap; no effect on HTTP |

### 12. A realistic service model

✅ Everything below compiles standalone on Ballerina 2201.13.3. Probes: `scratchpad/pathparam/`
and `scratchpad/blackbox/`.

#### The shared module

```ballerina
public type Service distinct service object { };

public enum Direction { ASC, DESC }
public type Page record {| int size = 25; int offset = 0; |};

public type Error distinct error;
public type NotFoundError distinct Error;
public type AlreadyExistsError distinct Error;
public type ConstraintViolationError distinct Error;

public annotation ServiceConfiguration ServiceConfig on type;  // neutral: page defaults/caps
public annotation HttpConfig    Http      on type;   // optional per-protocol override
public annotation GraphqlConfig Graphql   on type;   // optional per-protocol override
public annotation OverrideConfig Override  on object function;
public annotation ExposeConfig   Expose    on object function;
```

The model includes only `*dataservice:Service` — **never** `*http:Service` or `*graphql:Service`. Those
belong to the generated services, one per protocol.

#### Types

```ballerina
# Exposed type. The field list IS the exposure rule.
public type Emp record {| int id; string name; string email; Grade grade;
                          time:Date hiredOn; int departmentId; |};

public type EmpCreate record {| string name; string email; Grade grade;
                                time:Date hiredOn; int departmentId; |};
public type EmpPatch  record {| string name?; string email?; Grade grade?;
                                int departmentId?; |};

# Query capability: filterable fields, and the operators each admits.
public type EmpFilter record {|
    dataservice:Operation[] email        = [dataservice:EQ, dataservice:IN];
    dataservice:Operation[] grade        = [dataservice:EQ, dataservice:IN];
    dataservice:Operation[] hiredOn      = [dataservice:GTE, dataservice:LTE];
    dataservice:Operation[] departmentId = [dataservice:EQ, dataservice:IN];
    dataservice:Operation[] name?;   # no initializer = every operator valid for the type
|};

# Sortable fields. The members are the whitelist. Direction is not declared — it is
# per request, and every sortable field sorts both ways.
public enum EmpSortBy { name, hiredOn, grade }
```

Selection needs no type of its own: `Emp` above marks `email` and `hiredOn` optional, and that
is the declaration.

#### The service

```ballerina
@dataservice:ServiceConfig {defaultPageSize: 25, maxPageSize: 500}
@dataservice:Http    {basePath: "/api/v1"}                 // optional - default is /api
@dataservice:Graphql {basePath: "/graphql", maxDepth: 3}   // optional - default is /graphql
public type StoreService service object {
    *dataservice:Service;

    // ---- Emp, full CRUD
    @dataservice:Scopes {read: ["emp:read"], write: ["emp:write"]}
    resource function get    emps(EmpFilter filter, EmpSortBy[] sort, dataservice:Page page)
        returns Emp[]|dataservice:Error;
    resource function get    emps/[int id]()               returns Emp|dataservice:Error;
    resource function post   emps(EmpCreate data)          returns Emp|dataservice:Error;
    resource function put    emps/[int id](EmpPatch data)  returns Emp|dataservice:Error;
    resource function delete emps/[int id]()               returns Emp|dataservice:Error;

    // ---- Department, read only. No write methods, so none exist.
    resource function get departments(dataservice:Page page)  returns Department[]|dataservice:Error;
    resource function get departments/[int id]()      returns Department|dataservice:Error;

    // ---- relations, as hierarchical paths
    resource function get departments/[int id]/emps(EmpFilter filter, dataservice:Page page)
        returns Emp[]|dataservice:Error;
    resource function get emps/[int id]/department() returns Department|dataservice:Error;

    // ---- an override: not CRUD-derivable, so it carries its own query
    @dataservice:Override {
        query: "SELECT d.name AS departmentName, COUNT(e.id) AS headcount " +
               "FROM Department d LEFT JOIN Emp e ON e.departmentId = d.id " +
               "GROUP BY d.id, d.name"
    }
    resource function get headcount(HeadcountFilter filter, dataservice:Page page)
        returns Headcount[]|dataservice:Error;
};

# The override's return type IS its schema.
public type Headcount record {| string departmentName; int headcount; |};

# Filter capability over the override's OWN columns, not an entity's.
public type HeadcountFilter record {|
    dataservice:Operation[] headcount      = [dataservice:GTE, dataservice:LTE];
    dataservice:Operation[] departmentName = [dataservice:STARTS_WITH];
|};
```

#### Many-to-many

persist rejects n:n outright — `PERSIST_420: many-to-many relation is not supported yet`. So the
join table is its own entity, and the model exposes both it and the traversal:

```ballerina
// the join entity in its own right, composite key
resource function get    empprojects()                                 returns EmpProject[]|dataservice:Error;
resource function get    empprojects/[int empId]/[int projectId]()      returns EmpProject|dataservice:Error;
resource function post   empprojects(EmpProjectCreate data)             returns EmpProject|dataservice:Error;
resource function delete empprojects/[int empId]/[int projectId]()      returns EmpProject|dataservice:Error;

// the traversal, both directions
resource function get emps/[int id]/projects(dataservice:Page page)             returns Project[]|dataservice:Error;
resource function get projects/[int id]/emps(EmpFilter f, dataservice:Page p)  returns Emp[]|dataservice:Error;
```

The hierarchical path is what makes this work. A flat naming scheme collided — `empProjects`
meant both "the join rows" and "an employee's projects". Distinct paths, no clash. The composite
key is also stated structurally, so there is no question which arguments are key and which are
filter.

#### Per-protocol exposure

Absence is global: an undeclared method exists in no protocol. To vary by protocol, mark the
operation:

```ballerina
@dataservice:Expose {protocols: ["http"]}
resource function delete emps/[int id]() returns Emp|dataservice:Error;
```

Default is every generated protocol. Only divergent operations carry a marker.

Worth knowing: this is **finer-grained than any shipping product**. Azure DAB toggles protocols
per *entity* (`rest.enabled` / `graphql.enabled`); ZenStack and Directus offer nothing and rely
on shared permissions; Hasura gets per-operation control only because its REST surface is
hand-curated. Our model is operation-shaped, so per-operation is the natural granularity for us,
but we should not claim it as a category norm.

#### How every part of §11 is expressed

| Concern | Expressed by |
|---|---|
| Base path | `@dataservice:Http {basePath}` / `@dataservice:Graphql {basePath}` on the type - both optional |
| Operation | the resource method — accessor plus path give *(entity, verb)*, return type gives cardinality |
| Naming | the entity name in the resource path |
| Read shape | the return type's field list |
| Query capability | the **parameter types** — `EmpFilter` lists operators per field, `EmpSortBy` the sortable fields. Direction is not declared |
| Write | `EmpCreate` / `EmpPatch`, checked for totality against `EmpInsert` |
| Errors | `dataservice:Error` and its distinct subtypes |
| Relations | a hierarchical path — `departments/[int id]/emps` |
| Composite keys | consecutive path segments |
| Override | `@dataservice:Override {query}` plus a return type that is its own schema |
| Per-protocol exposure | `@dataservice:Expose {protocols}` |
| Absence | **a missing method means a missing operation** |

Query capability lives in the **parameter types** — not in an annotation, and not on a service
class.

#### The convention that makes an operation derivable

| Shape | Operation |
|---|---|
| `get <entities>` | collection read |
| `get <entities>/[key]` | single read |
| `get <parents>/[key]/<relation>` | relation traversal |
| `post <entities>` | create |
| `put <entities>/[key]` | partial update |
| `delete <entities>/[key]` | delete |
| anything else | **must carry `@Override`**, or it is a diagnostic |

#### One wrinkle found while compiling

An enum member imported from another module must be qualified: `direction = dataservice:ASC`, not
`= ASC`, which fails with `undefined symbol 'ASC'`.

### 13. Black-box results

Three data models against four protocol combinations. All compile.

| | REST only | REST CRUD + GQL read | GQL read + mutation | REST + GQL full |
|---|---|---|---|---|
| single entity | pass | needs `@dataservice:Expose` | pass | pass |
| 1:n relation | pass | needs `@dataservice:Expose` | pass | pass |
| n:n + entity | pass | needs `@dataservice:Expose` | pass | pass |

Four gaps were found and three are now closed by the path-parameter form:

| | Gap | Status |
|---|---|---|
| G1 | REST CRUD plus GraphQL read-only is not expressible — absence is global | **closed** — `@dataservice:Expose` |
| G2 | n:n traversal collided with the join entity's own name | **closed** — distinct paths |
| G3 | no way to tell a key argument from a filter argument | **closed** — key is a path segment |
| G4 | GraphQL binding had to infer the relation parent from a method name | **closed** — the path states it |
| G5 | no way to replace a whole relation set | **open, deferred** — see below |

#### G5, deferred with the shape known

Replacing a set — "this employee is now on projects 4 and 5, not 1, 2, 3" — takes five calls
today, none of them atomic, and the client must know the current set first.

The shape is settled and has prior art (Spring Data REST's `PUT … text/uri-list`, JSON:API's
`PUT/PATCH /:type/:id/relationships/:relationship`):

```ballerina
resource function put    emps/[int id]/projects(int[] projectIds) returns Project[]|dataservice:Error;
resource function post   emps/[int id]/projects(int[] projectIds) returns Project[]|dataservice:Error;
resource function delete emps/[int id]/projects(int[] projectIds) returns Project[]|dataservice:Error;
```

Three reasons it is not v1:

- **It needs a transaction.** Replace is delete N plus insert M, atomically. Nothing else in the
  design needs one yet.
- **An id list is not always enough.** A join row carrying its own columns (`EmpProject.role`)
  cannot be replaced by `int[]`; it needs the full rows. One concept, two shapes — and that rule
  has to be settled before anything can be generated.
- **It is the same family as something already deferred** — `spec/02-http.md` defers collection
  `DELETE`/`PATCH` by filter for needing a filter-scoped bulk path.

### 14. What the UI has to offer

The model will mostly be authored through a UI, so it is worth stating what that UI must expose.

The two existing WSO2 service UIs are shaped by their protocol:

| HTTP service UI | GraphQL service UI |
|---|---|
| HTTP method | Query / Mutation / Subscription |
| Resource path | Field name |
| Path params, query params, headers | Arguments |
| Payload, response codes | Return type |
| CORS, compression, chunking | `maxQueryDepth`, introspection, GraphiQL |
| imports OpenAPI | imports a GraphQL schema |

A data service author sets none of that. They pick entities and operations; paths, methods,
field names and arguments are all derived. So **one model, one UI, and that UI is a third shape**
— not the HTTP one, not the GraphQL one.

| Level | What the user sets |
|---|---|
| Service | base path; which protocols to generate; port per protocol |
| Entity | include or exclude; which operations exist |
| Operation | **an operation × protocol grid** — this is `@dataservice:Expose`, and neither existing UI has anything like it |
| Read | result fields; filter fields with operators per field; sortable fields; page defaults |
| Write | payload fields |
| Relation | navigable or not, and direction |

Genuinely protocol-specific settings — CORS, auth, compression, `maxQueryDepth`, introspection,
GraphiQL — belong in a thin per-protocol tab, reusing the existing screens.

The entry point differs too. HTTP imports OpenAPI and GraphQL imports a schema; a data service
imports neither, because its schema comes from the database via `persist pull`.

### Module naming and diagnostic codes

Two decisions from `02-shared-module.md` are design-level and survive the replacement.

#### The name

**Settled: `dataservice`, for everything.** One word covers the tool, the tool package, the
runtime library and the annotations.

| | |
|---|---|
| Command | `bal persist add --dataservice` |
| Tool package | `ballerina/tool.dataservice` |
| Runtime library | `import ballerina/dataservice` |
| Annotation | `@dataservice:Override` |

Tools publish under `ballerina/tool.<id>` and libraries under `ballerina/<name>` — verified from
`tool.persist` in the local package cache — so the tool and the library share the name without
colliding.

The org is `ballerina`, not `ballerinax`. The dividing line between the two is not whether
something is a standard, but **whether the module binds to a specific external system**.
`ballerinax` holds `mysql`, `salesforce`, `kafka`; `ballerina` holds `persist`, `workflow`,
`constraint`. A data service binds to none of them.

#### Diagnostic codes

A new range, `DATASERVICE_xx`, rather than extending `PERSIST_CLIENT_xx`. The existing persist
codes are allocated chronologically with no documented convention, and mixing a new feature into
that sequence makes both harder to read.

| Range | Area |
|---|---|
| `DATASERVICE_1xx` | model file structure |
| `DATASERVICE_2xx` | entity and field references |
| `DATASERVICE_3xx` | payload type mapping |
| `DATASERVICE_4xx` | override and query validation |
| `DATASERVICE_5xx` | protocol-specific |

#### What moved to the implementation

Dropped from the proposal, not from the product: the annotation inventory, `constraint`
integration, `jsondata` integration, and the defaulted-fields gap. All are module internals.
They belong in the module's own documentation once it exists.

## Part B — the tool and its lifecycle

### Why a command on persist, not a separate tool

An earlier draft gave the data service its own build tool and its own `bal ds` CLI. The
reasoning then was that a `--dataservice` **flag on `generate`** kept producing friction: a
flag smuggled under `options`, `persist add` becoming an upsert, a schema key, a cache key.

That reasoning attacked the wrong shape. The friction came from making it a *modifier on an
existing command*, not from it living in persist. **A new command has none of those
problems**, and a separate tool bought its own:

| | Separate `ds` tool | New `persist` command |
|---|---|---|
| Generator code | lives in `persist-core` regardless | same |
| Cache invalidation when `model.bal` changes | a **cross-tool** dependency to declare | one tool, one cache |
| Version skew | `ds` built against an older `persist-core` reading a newer model | impossible |
| Packaging | inside `persist-tools` with a second entry point, or its own package? | settled |
| New CLI surface | three commands — `add`, `sync`, `generate` | **one** — `add` and `generate` already exist |
| Discoverability | user must know `bal ds` exists | `bal persist --help` |

The generator was always going to live in `persist-core` — it reuses the parsed model, the
pluraliser, the syntax helpers and the build hook. A separate CLI was packaging layered on
shared code, and it bought two new problems to solve for one it avoided.

#### What comes back

Two prerequisites the separate-tool draft had removed:

- **`persist-options-schema.json`** has `additionalProperties: false`, so `options.dataservice`
  must be added or the build rejects the toml.
- **The codegen cache key** hashes only the model file, so an edit to the spec would be
  skipped on a warm cache.

The second is worth reframing. Per D75 it is a **pre-existing bug** — `eagerLoading` has it
today — and this feature only makes it visible. Folding into persist means fixing it; the
separate tool routed around it and left it broken for existing users.

### What ships where

| | |
|---|---|
| CLI | `bal persist` — one new command, `expose` |
| Toml | `[[tool.persist]]`, with a new `options.dataservice` group |
| Generator | `persist-core`, beside the existing client generators |
| Runtime library + compiler plugin | `ballerina/dataservice` — annotations, neutral types, spec validation |

`persist-core` already exports everything the generator needs:
`io.ballerina.persist.models` for `Module`/`Entity`/`EntityField`/`Relation`, `inflector` for
`Pluralizer`, `utils` for `CaseConverter`, and `nodegenerator.syntax.*` for the emission
helpers. No new exports required.

**The name lives in the library, not the command.** `ballerina/dataservice`, the
the `@dataservice:` annotations and the `DATASERVICE_xxx` diagnostic
range all carry it, and `--dataservice` puts it in the CLI where a user meets it first. The
new command is a verb, matching `init`/`add`/`pull`/`push`/`generate`/`migrate`.

### Commands

One new command. `add` and `generate` already exist and simply do more.

| Command | Records the options | Derives the spec | Generates code |
|---|---|---|---|
| `bal persist add --dataservice http,graphql` | yes | yes, when the model has entities | no — `bal build` does |
| `bal persist expose` | no | yes | no |
| `bal persist generate` | no | **never** | yes, one-shot |

That last cell is why `expose` is a separate command rather than something folded into
`generate`. **`generate` only ever writes `generated/`, which is tool-owned.** Having it
touch `persist/service.bal` — a user-owned, hand-edited file — would break the ownership
boundary the whole design rests on.

#### Why the command is `expose`

Candidates and why they were rejected:

| | Reads as | Collides with |
|---|---|---|
| `sync` | reconciling two projections | `pull` — a sibling command, so a user assumes it hits the database |
| `refresh` | overwrite and redo | it appends; regeneration is additive only |
| `serve` | starts a server | it writes a file |
| `publish` | ships a package | `bal push`, Ballerina Central |
| `export` | dumps a read-only artifact | DAB's `dab export --graphql` does exactly that; ours is a file you edit |
| `scaffold` / `draft` | a first run only | it runs every time the model changes |
| `project` | — | "Ballerina project" |

`expose` reads correctly on the first run and every run after — *"expose the new entity
too"* — where `scaffold` is a first-run word for a repeated command. `derive` was the
runner-up, more literally accurate but abstract in a help listing.

Help text: **"expose — derive a data service spec from the model"**. Phrased that way rather
than "expose the model", because the one real risk with the verb is implying it starts
serving something. It writes a file.

#### `bal persist expose` — derive the spec from the model

The same relationship `persist pull` has to a database, one level up:

| Tool | Upstream source of truth | Derived hand-written artifact |
|---|---|---|
| `persist` | the database | `persist/model.bal` |
| `dataservice` | `persist/model.bal` | `persist/service.bal` |

Run it whenever the model changes. It is idempotent: entities already covered are left
alone, new entities get resources and payload types appended.

> **It appends. It does not overwrite — and that is the opposite of `persist pull`.**

`persist pull` rewrites `model.bal` wholesale, after a y/n warning, because the database is
the *whole* source of truth and the model is a pure projection of it. The spec is only half
derived. The other half is hand-written: deleted resources, `@Override` SQL, auth
annotations, renamed root types. Clobbering would destroy all of it.

| | `persist pull` | `persist expose` |
|---|---|---|
| Existing file | overwritten | appended to |
| Prompt | `WARNING ... Continuing would overwrite it. (y/n)` | none needed |
| Hand edits | lost | preserved |

`--force` opts into persist's behaviour — discard the spec and re-derive from scratch —
with the same y/n warning. For starting over deliberately.

#### Flags

| Flag | On | Meaning | Default |
|---|---|---|---|
| `--dataservice <http,graphql>` | `add`, `expose` | enable the data service and record its protocols | off on `add`; reads the toml on `expose` |
| `--force` | `expose` | discard the spec and re-derive, with a y/n warning | off |

`--dataservice` is **recorded**, as `options.dataservice.protocols`. It accepts several
values — `--dataservice http,graphql` — and on a later `expose` it **appends** to the list
rather than replacing it, the same additive semantics as the spec file itself.

`soap` and `odata` are not accepted values yet. Passing them is an error naming the supported
values, rather than a silently ignored flag.

There is no `--model`: one package has one persist model. There is no `--id` or `--module`:
there is one `[[tool.persist]]` block, and `targetModule` defaults.

#### `add` derives the spec, when it can

`bal persist add --dataservice http,graphql` records the options and then runs `expose`.

But it cannot always. **D68: `bal persist add` writes a `model.bal` containing only
`import ballerina/persist as _;`** — no entities. A spec derived at that moment would be
empty. D68's existing rule already covers this and transfers unchanged: with no entity in the
model it is an error naming the next command, stated about the model rather than per-command.

| Situation | Behaviour |
|---|---|
| `add --dataservice`, model has entities | records the options, runs `expose`, spec comes out populated |
| `add --dataservice`, model empty | records the options, then errors naming `expose` to run once entities exist |
| `expose` re-run | appends entities that have no resources; touches nothing existing |
| `generate` | never writes `persist/service.bal` |

### `Ballerina.toml`

One block, not two. The data service is an options group on the persist block.

```toml
[package]
org = "acme"
name = "app"
version = "0.1.0"

[[tool.persist]]
id = "db-client"
targetModule = "app.store"
filePath = "persist/model.bal"
options.datastore = "mysql"
options.dataservice.filePath = "persist/service.bal"
options.dataservice.protocols = ["http", "graphql"]
```

Two new keys, both under `options.dataservice`. Absent, persist behaves exactly as today.

| Key | Written by `add --dataservice` | Purpose |
|---|---|---|
| `options.dataservice.filePath` | yes | the spec file |
| `options.dataservice.protocols` | yes | which protocols to generate |
| `targetModule` | no | existing persist key; the service module defaults to `<targetModule>.api` |


#### Why `filePath` is still declared

Under pure file-presence, `rm persist/service.bal` would silently delete the entire API
on the next build. A declared path makes that a loud error instead. Same footgun as resource
deletion, same answer — and it follows persist's own convention, since `filePath` already
names `persist/model.bal` in the same block (D72).

#### Why `protocols` is here and not in the spec

The service model is protocol-independent — that is the thesis of Part A. A spec file
that names its protocols is not. With the list in the manifest, **the default spec file
mentions no protocol at all**; protocol names appear in it only when someone deliberately
diverges from a default path.

This **reverses D65**, which read the protocol from the service type's inclusion
(`*http:Service` vs `*graphql:Service`). D65's justification was that a single
`options.dataservice` *string* could not express two protocols at once. An array can, and the
inclusion approach carried a cost D65 did not price: a second protocol needed a second root
type and a second spec file, duplicating every resource, filter type and payload type. The
spec's root type now includes only `*dataservice:Service`.

#### Why there is no `persistId`

The separate-tool draft needed `options.persistId` so its block could name the persist block
it was built over. With one block there is nothing to point at, and with one persist model per
package there would be nothing to choose anyway. It is gone, not merely optional.

#### What the generator reads from the same block

Everything it needs is already there, which is the mechanical argument for one block:

| Reads | Uses it for |
|---|---|
| `filePath` | the model to validate the spec against |
| `targetModule` | the client module to import, and the base for the service module |
| `options.datastore` | to reject query features the datastore cannot support |
| `options.eagerLoading` | array returns instead of streams |

Under the separate tool each of these was a cross-block lookup. Here they are siblings.

#### `targetModule` default

`<persist targetModule>.api` — so `app.store` gives `app.store.api`.

Output directory follows persist's convention of stripping the package prefix, so
`app.store.api` writes to `generated/store/api/`. Noted because tools differ here: persist
strips the prefix, `openapi` does not. Matching persist keeps one project's `generated/`
tree internally consistent.

### One data service per package

**Scope decision: a package with a data service has exactly one persist model and one
service model.**

This is stricter than an earlier draft, which allowed several persist models and let *one* of
them have the data service. That rule was arbitrary — with two models in a package, nothing
explained why only one could be exposed.

The rule follows from the deployment unit. **One package is one deployable.** Two APIs are
two deployables, so they are two packages. A package that wants two data services is telling
you it should be split.

| | Result |
|---|---|
| Several entities in one model | one service, all entities under one base path |
| Several persist models **and** a `[[tool.persist]]` entry | **error**, naming every model found and telling the user to split the package |
| A persist model with no data service | normal — the client is still generated |
| Same model over REST *and* GraphQL | **one** entry, `options.dataservice.protocols = ["http", "graphql"]` |

This is ZenStack's rule exactly: "every model needs to include exactly one datasource
declaration", inherited from Prisma, with multi-file schemas merged into one before
processing. Azure DAB does allow several sources through a `data-source-files` array — but
that **merges** them into one API with globally unique entity names and no cross-source
relationships. It is not n APIs from n sources. Nobody generates that.

Nor does this foreclose the DAB behaviour: one service model spanning several stores would be
a new feature layered on top, not something this restriction blocks.

Cross-store APIs are out of scope for a second reason: no code generator does them. Azure
Data API builder allows several data sources in one API but forbids relationships across
them; only Hasura joins across sources, and only because it is a runtime query planner. See
`prior-art.md` section 13.

#### Why restricting it is better

Restricting to one service does not only narrow scope, it deletes machinery. An earlier
draft of this proposal carried a table of port and base-path defaults, a rule for which
model gets `8080`, and a scheme for prefixing configurables per service type. All of it
existed to manage collisions between sibling services.

With one service per module those collisions cannot occur:

| Collision | Why it is gone |
|---|---|
| The service's `port` vs persist's `port` | different modules — `Config.toml` separates them by section |
| Two services both wanting `8080` | there is no second service |
| Two services sharing a base path | same |
| Two service types in one module | one root type per spec file |

#### Two protocols, one entry, two listeners

One package, one spec file, one entry:

```toml
[[tool.persist]]
id = "dataservice"
filePath = "persist/service.bal"
options.dataservice.protocols = ["http", "graphql"]
```

The generator emits **two service declarations into one module, on two listeners and two
ports.** Not one listener with two paths.

That is a deliberate departure from both comparable products, so the reasoning matters.
Azure DAB serves REST at `/api`, GraphQL at `/graphql` and MCP at `/mcp` in one process on
one port — it has no port setting in its configuration at all, because Kestrel owns the
listener. ZenStack mounts each handler on the host's Express app with `app.use(...)`, so the
host owns the port. **Neither chose one port; neither owns a listener to choose with.** A
generated Ballerina artifact does, so the precedent does not transfer.

Two listeners buy three things:

- **`basePath` stays genuinely per-protocol without collision logic.** On one port the two
  protocols must occupy different paths and the generator needs prefix-collision rules. On
  two ports they cannot collide at all.
- **Independent exposure.** GraphQL internal-only with REST public is a firewall rule, not an
  ingress path rule. It is a real requirement and one port makes it awkward.
- **No listener-sharing machinery.** Constructing a `graphql:Listener` from an
  `http:Listener` is avoided entirely, along with having to verify that it works.

Configurables stay distinct because the generator owns both names — `restPort` and
`graphqlPort`. The collision machinery deleted above does not return: there is no sibling
service to collide with, only two names emitted by one generator.

#### Defaults

Load-bearing now, rather than examples.

| | Default | Override |
|---|---|---|
| HTTP base path | `/api` | `@dataservice:Http {basePath: "/api/v1"}` |
| GraphQL base path | `/graphql` | `@dataservice:Graphql {basePath: "..."}` |
| HTTP port | `8080` | `Config.toml` |
| GraphQL port | `8081` | `Config.toml` |

Paths match DAB's defaults exactly. Note the HTTP default carries **no version segment** —
versioning becomes a deliberate act through `@dataservice:Http`, rather than something baked into
every scaffold.

Ports get real defaults rather than `= ?`. D54 argued for a required value specifically to
stop sibling services clashing on a port; with one data service per package there is no
sibling, so a default is safe and friendlier.

#### The protocol annotations are optional overrides

`@dataservice:Http` and `@dataservice:Graphql` tune a protocol that `options.dataservice.protocols` has already declared.
They do not declare it. With no annotation, the defaults above apply, and the common spec
file names no protocol at all.

An annotation for a protocol not listed in `options.dataservice.protocols` is an **error** naming both
the annotation and the manifest — never a silent ignore. Same reasoning as the declared
`filePath`: loud beats silent. The reverse — protocols declared with no annotations — is the
normal case and needs no diagnostic.

#### Generated file names

From the root service type name, snake-cased — `StoreApi` gives `store_api.bal` and
`store_api_service.bal`. `CaseConverter` in the tool model already does this conversion.

### File layout

```
persist/model.bal                       USER   persist tool input
persist/sales/model.bal                 USER   second model
persist/service.bal                 USER   data service spec
persist/sales/service.bal           USER   second spec
generated/store/persist_types.bal       TOOL   persist: entity types
generated/store/persist_client.bal      TOOL   persist: client
generated/store/persist_db_config.bal   TOOL   persist: database configurables
generated/store/script.sql              TOOL   persist: DDL
generated/store/api/<name>.bal          TOOL   dataservice: service object type + payload types
generated/store/api/<name>_service.bal  TOOL   dataservice: implementation + listener
Config.toml                             USER   values for both modules' configurables
```

Two tools, one input folder each, two output modules under `generated/`. No file and no folder
has mixed ownership.

#### Why the spec lives in `persist/`

One CLI, one directory. The data service is a command on `bal persist`, so its input sits beside
the model the command reads:

```
persist/model.bal      the data model
persist/service.bal    the API surface
```

One consequence to handle. The persist compiler plugin claims `.bal` files as models by *folder*,
never by filename (`Utils.java:225-295`: parent ends with `persist`, or grandparent for
multi-model), so `persist/service.bal` is claimed. It is rejected with `PERSIST_101` as soon as
anything compiles it — including an IDE, which compiles single files, so a user editing the spec
would see a spurious error.

The mitigation is free: **the spec does not import `ballerina/persist`**, and the plugin only
activates when the compiled unit does. It imports `ballerina/dataservice` and the protocol
module, and has no need for persist. The prefix is the plain `dataservice:` with no `as` alias,
which also stays clear of `PERSIST_102`.

Fixing the gate to claim only the file named in `filePath` is still worth doing — the diagnostics
are actively misleading, and a user will add the import by habit — but nothing here waits on it.
Proposal 5 carries the change.

`persist/` is not a package source root, so the IDE story is unchanged either way — the spec
compiles standalone but is not checked against the model until `bal build`.

### Where the code lives

Three artifacts, two of them new packages. Worth being explicit, because the split decides what
ships when.

| Artifact | What it is | Holds |
|---|---|---|
| `ballerina/dataservice` | runtime library + compiler plugin | the annotation declarations (`@dataservice:ServiceDef`, `@dataservice:Override`, `@dataservice:Expose`, `@dataservice:Scopes`, `@dataservice:Entity`), the neutral types (`dataservice:Service`, `dataservice:Page`, `dataservice:Direction`, `dataservice:Error` and its subtypes), and any public function the generated service calls at runtime |
| `bal persist` | CLI build tool | `add`, `sync`, `generate`; reads the model and the spec, writes `generated/` |
| `persist-tools` / `persist-core` | existing | reused for the parsed model, the pluraliser and the syntax helpers |

Two things this pins down:

**The annotations must live in a package the spec imports.** A Ballerina annotation is only
usable where it is declared and imported, so `ballerina/dataservice` is a hard prerequisite for
anything annotation-based — the auth scopes in Part A §10 included. It ships before the tool
is useful.

**The compiler plugin belongs with the library, not the CLI.** Validating the spec against the
model happens at `bal build`, which is plugin territory. In the CLI, diagnostics would appear
only when the user runs a command, not when they build.

One open item: `bal persist` reuses persist-core for model parsing. Whether it ships inside
`persist-tools` with a second entry point, or as its own package depending on persist-core,
decides release cadence and version skew — a `bal persist` built against an older persist-core reading
a newer `model.bal` is the failure mode. **Not settled.**

#### Cache invalidation now crosses two tools

`bal persist generate` must invalidate when `persist/service.bal` changes, not only when
`persist/model.bal` does. Today the cache key covers the model file alone, so an edit to the
spec is skipped on a warm build. The key has to widen to cover both input files and the
`options.dataservice` block of `[[tool.persist]]` — proposal 4 carries this as blocking.

### Who writes what

**Only `bal persist add --dataservice` and `bal persist expose` write into `persist/`. Build-time
generation only reads it.**

That matters because `bal build` runs the tool on every build. A build must never edit a
hand-written source file — no surprise diffs, no fighting the editor.

| Situation | Behaviour |
|---|---|
| `add`/`pull`, no spec file | derive it: every entity, full CRUD, no auth |
| `add`/`pull`, spec exists | append what is missing |
| `pull --force` | discard and re-derive, after a y/n warning |
| `bal build`, spec exists | read it, validate it, generate from it — never edit it |
| `bal build`, `filePath` names a missing file | error naming the missing file |
| no `[[tool.persist]]` block | do nothing, even if a spec file happens to be there |
| model gains an entity | not exposed until `bal persist expose` is run again |
| model loses an entity still named in the spec | validation error naming the resource |

A new table not being exposed automatically is deliberate. Publishing an API endpoint is a
decision, not a side effect of introspection — which matters most after
`bal persist pull` against a database full of audit and credential tables.

#### Additive only

Regeneration may **append** to the spec. It may never rewrite, reorder or remove.

That is what removes the need for a preserve-list. `prisma db pull` rewrites the schema and
therefore publishes a documented list of annotations it re-grafts; `zen db pull` does the
same job without such a list and dropped `@email` attributes and `///` comments until a bug
fix. Appending only means there is nothing to preserve.

The cost: an entity removed from the model is not removed from the spec. It surfaces as a
validation error, which is the right outcome — silent endpoint removal would be worse — but
it is a manual edit.

#### When the model changes

The most common question about the two-file split. The short answer is that **there is no
merge, because nothing is ever rewritten** — and what replaces a merge is a diagnostic with a
file and a line number.

Every model change falls into one of two buckets.

| Change in `model.bal` | What happens to `persist/service.bal` |
|---|---|
| new entity | nothing, until you run `bal persist expose` — then resources and payload types are **appended** |
| new column | nothing, ever. Add the field to the payload type by hand to publish it |
| new relation | nothing. Relation resources are opt-in in both directions |
| renamed column | **build error** on the payload type field |
| dropped column | **build error** on the payload type field |
| changed column type | **build error** — and a second one if a declared `Operation` no longer applies to the new type |
| dropped relation | **build error** on the relation resource |
| cardinality flipped `1:n` → `n:1` | **build error** — `Employee[]` no longer matches |
| dropped entity | **build error** on every resource and payload type naming it |

Additive changes are silent and opt-in; **publishing is a decision, not a side effect of
introspection.** That matters most right after a `bal persist pull` against a database full of
audit and credential tables. Destructive changes are loud and never silent — the endpoint
cannot quietly start returning the wrong shape, because the build stops.

The one thing the tool does not do is rename for you. A column rename reaches the spec as a
dropped field plus an unknown field, and you fix the payload type. **No comparable tool does
better**, because introspection cannot distinguish a rename from a drop-plus-add.

#### What everyone else does

Four strategies exist. Nobody merges two hand-written artifacts.

| Strategy | Who | On a model change | What it costs |
|---|---|---|---|
| **No artifact** — the schema *is* the API | PostgREST, Spring Data REST | reflected immediately | you had no control surface to lose: hiding a column means creating a view |
| **Pattern + template, expanded at startup** | DAB `autoentities` — `--patterns.include "dbo.%"`, `--patterns.exclude "dbo.internal%"` | a new matching table is exposed automatically on next start | one permission set and one template for everything matched; per-entity control means leaving the pattern |
| **Rewrite, with a documented preserve-list** | `prisma db pull` | file rewritten; a named subset of your edits re-grafted | the list is finite. Prisma keeps `@map`, `@@map`, `@updatedAt`, custom `@relation` names and block order — and **does not** keep field order within a model or custom defaults. `zen db pull` attempts the same job without a list and dropped `@email` and `///` comments until a bug fix |
| **Separate artifact + drift report** | Hasura `metadata inconsistency list`, `dab validate`, Directus | nothing is merged; you are told what no longer resolves and you fix it | a manual edit per drifted item |

We are the fourth, moved earlier. `dab validate` stage 5 checks *"included/excluded fields
exist"* and *"policies reference valid fields"* against the live database, and Hasura returns
an `inconsistent_objects` array with a reason per object — both at deploy time. Ours is the
same check at `bal build`, against `model.bal` rather than a live connection, with a
`DATASERVICE_xx` code and a source location.

Prisma is the only one that rewrites-and-preserves, and the reason is instructive: **their
schema file is the data model and the exposure model at once**, so a rewrite necessarily
touches hand-written content, so a preserve-list is forced. Splitting the two files is what
lets us clobber the derived one freely — `bal persist pull` already does exactly that — and
never touch the other.

#### `expose` reports as well as appends

The validator already computes the drift, so `bal persist expose` prints it rather than making
you discover it one build error at a time:

```
$ bal persist expose

  +  Timesheet            appended — 5 resources, 3 payload types
  ~  Employee.email       column dropped from the model
                          persist/service.bal:24  still names it
  ~  Employee.grade       type changed: string -> enum Grade
                          persist/service.bal:71  [GTE, LTE] no longer applies
  -  Contractor           entity removed from the model
                          persist/service.bal:60-78  5 resources still name it

  1 entity appended, 3 items need an edit. Run `bal build` for the diagnostics.
```

Appends are applied. The rest is reported and left alone — this is Hasura's
`inconsistency list` and DAB's `validate` stage 5, folded into the command you were going to
run anyway. `--force` remains the escape hatch for starting over.

### Configurables

The generated service lives in its own module, so persist's `port`, `host`, `user`,
`database`, `password` and `connectionOptions` are not in scope. `Config.toml` separates the
two by module section:

```toml
[app.store]                  # persist's module
host = "localhost"
port = 3306
user = "root"
password = ""
database = "sales"

[app.store.api]              # the data service's module
listenerPort = 8080
listenerHost = "0.0.0.0"
```

The service's own values take **distinct names** — `listenerPort`, not `port` — so that
reading `Config.toml` is unambiguous even though the sections already separate them.

#### Defaults

| Value | Default |
|---|---|
| `listenerPort` | `8080` |
| `listenerHost` | `"0.0.0.0"` |
| base path | `/` for the only data service in a package |

A single default port is safe here precisely because there is one service per package. Two
listeners cannot share a port, and two services cannot share a base path — verified: sharing
a base path compiles and then fails at startup with `Service registration failed: two
services have the same basePath`. Where a second entry exists for a second protocol, its
port must be set explicitly in `Config.toml`; the generator emits `= ?` for it, turning an
"address in use" crash into a startup configuration error naming the missing value.

### Datastore limits

The tool reads `options.datastore` from the referenced persist block and rejects what that
store cannot do:

| Datastore | Data service |
|---|---|
| `inmemory` | allowed, but no filtering, sorting or paging |
| SQL store | full surface |

The `inmemory` restriction is a real limitation, not a policy choice. Verified: the
generated in-memory client has no `whereClause`, `orderByClause` or `limitClause`
parameters at all — those exist only on SQL clients. A spec asking for query parameters
against an in-memory store is a validation error, not a silent no-op.

### Validation and diagnostics

The tool validates the spec against the model and reports through
`ToolContext.reportDiagnostic`, with a location in the spec file, so errors read like
compiler errors.

| Check | Example |
|---|---|
| every resource is CRUD-derivable, or carries `@Override` with SQL | neither is an error |
| entity named in the spec exists in the model | catches a removed entity |
| field named in a payload type exists on the entity | catches a renamed column |
| query parameters are supported by the datastore | `inmemory` with `?limit=` |
| a sortable or filterable field is a real column | security-critical, ORDER BY is not parameterizable |
| root type includes `*dataservice:Service` and no protocol module | `*http:Service` on the spec's root type |

Diagnostic codes start a new `DATASERVICE_xx` range rather than extending persist's
`PERSIST_xx` sequence. The tool is shared now, but the namespace stays separate: these
diagnostics are about the service spec, and a reader seeing `DATASERVICE_03` should not have
to wonder whether it concerns the data model.

### Codegen cache

**This is the prerequisite the separate-tool draft removed, and it comes back.**

persist's cache hashes only the model file. Two consequences once the data service shares it:

| Input | Why it must be in the key |
|---|---|
| the model file | already there |
| the spec file | the primary data service input; editing it must not be skipped |
| `options.dataservice.*` | adding a protocol must not be skipped on a warm build |
| `options.*` generally | pre-existing gap — see below |

The last row matters more than it looks. Toggling `options.eagerLoading` today is **already**
skipped on a warm build, because the key covers only the model. That is a pre-existing persist
bug (D75); this feature does not create it, it makes it visible on the first run.

So folding into persist means fixing it. The separate tool would have routed around it with
its own cache and left `eagerLoading` broken for existing users — which, on reflection, was a
reason to fold in rather than a cost of doing so.

### `persist-options-schema.json`

The other returning prerequisite. The schema sets `"additionalProperties": false`, so
`options.dataservice` must be added there or the build rejects a manifest that uses it.

Mechanical, but it gates everything: without it, `bal persist add --dataservice` writes a
manifest the build then refuses.

### Backward compatibility

The promise is narrower than the separate tool's, and worth stating precisely rather than
claiming persist is untouched.

| | |
|---|---|
| No `options.dataservice` in the manifest | behaviour is byte-identical to today |
| Existing commands | unchanged; `expose` is additive |
| `persist-options-schema.json` | gains one optional key |
| Cache key | widens — a correctness fix, and the first build after upgrade re-runs |

The golden-file tests already enforce the first row, so any drift shows up as a test failure
rather than as a report from a user.

## Open questions

1. ~~Does `pull` preserve edits?~~ **Answered — it does not.** `bal persist pull` rewrites
   `model.bal` wholesale after a y/n warning, with no merge and no preserve-list. That is why
   the spec is a separate file: the derived one stays free to clobber.
2. **Service class or record for GraphQL entities without relations?** §7 argues service class
   for entities with relations; for the rest a record is simpler and loses nothing.
3. ~~How is query capability declared?~~ **Answered in §12** — in the parameter types.
4. ~~How deep may a path go?~~ **Answered in §7** — one hop, and not by choice. persist's
   `WithRelations` nests `Optionalized`, not `WithRelations`, so a deeper path has nothing to
   bind to. A deeper path in the spec is a diagnostic. `maxDepth` survives as a *runtime* cap for
   GraphQL only (§10).
5. **Per-protocol naming overrides.** §3 notes DAB needed them. We have only canonical name plus
   per-binding casing.
6. **G5 relation-set writes** — deferred; the two-shapes problem in §13 is what needs deciding.
7. **How does an auth scope render in GraphQL?** §10. `ballerina/graphql` has no per-resource
   auth annotation, so scope-per-operation is unproven as a neutral concept. Needs a probe before
   proposal 3 commits.
8. **Does §12's G2 disambiguation survive?** `empprojects` (the join entity) and
   `emps/[id]/projects` (the traversal) are distinct paths today. Confirm nothing in the
   `@dataservice:Entity {relations: false}` off-switch reintroduces the collision.

### What this proposal does not settle

- The `expose` command's exact help text and diagnostic wording.
- Whether `expose --force` prompts, or requires a second confirmation flag.
- Ordering guarantees if a future tool also writes into `persist/`.
